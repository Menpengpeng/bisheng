# Feature: F043-flow-assistant-sql-schema-cache（工作流助手节点：选表取 Schema + Schema 缓存）

> **本文档定位 — 纯 What（需求口径，不随代码漂移）**
> spec 只回答 **做什么 / 验收标准 / 不做什么**；所有 How（参数字段、缓存 key 规则、API、Service、前端组件、文件清单、方言适配）在 [design.md](./design.md) 与 [tasks.md](./tasks.md)。

**关联 PRD**: 工作流助手节点数据库能力增强（NL2SQL 场景降轮次、提准确率）
**优先级**: P1
**所属版本**: v2.6.0
**依赖**: 无（在既有「工作流助手节点 sql_agent 数据库开关」链路上增量改造，不依赖其他 v2.6.0 Feature）

> **范围边界**
>
> - **本次纳入**：
>   - **A. 助手节点绑定数据库后支持「选择表」**：配置态可拉取所连数据库的表清单、勾选若干表；运行态 SQL Agent 只在被勾选的表范围内发现与使用表结构，不再盲查全库表清单。
>   - **B. Schema 结构预取**：对勾选的表，运行时一次性获取其结构信息（表/列/类型等 DDL 级信息），直接提供给 SQL Agent，省去其运行中「列表 → 逐表取 schema」的多轮工具调用。
>   - **C. Schema 缓存开关**：可配置将获取到的 schema 结构写入缓存；开关开启时，后续运行命中缓存即直接使用、不再连库取元数据；提供手动「刷新缓存」手段应对表结构变更。
>   - **D. 配置态「获取表列表 / 测试连通」能力**：画布上填完连接信息后可一键拉取表清单（拉取动作即隐含连通性验证），支撑选表交互。
>   - **E. 数据库类型覆盖**：MySQL、PostgreSQL、Oracle、SQLServer、DB2、GaussDB、DM8（达梦）。
>
> - **本次明确排除**（附原因）：
>   - **独立「数据库节点」**（作为基础节点向任意下游节点输出 schema）——本期 schema 能力内聚在助手节点内，仅供该节点 SQL Agent 使用；若后续需跨节点复用，另起 Feature 并将缓存/取数服务下沉为公共模块。
>   - **数据源（连接）集中管理**（连接的 CRUD、复用、独立权限对象）——连接参数仍随节点配置保存，不新增数据源表与管理页面。
>   - **节点内执行任意 SQL / 返回数据行的新节点能力**——本期不改变「SQL Agent 自然语言查数」的执行模型，只改它获取表结构的方式。
>   - **数据库账号密码的加密存储改造**——现状密码随工作流配置明文落库，属既存问题；本期只承诺密码不进缓存 key、不进日志，加密存储另立任务。
>   - **SQL 写操作的强拦截（SQL 解析白名单 / 只读账号托管）**——沿用现状（提示词约束仅 SELECT）；本期在选表场景收窄 LLM 可用工具面，但不做服务端 SQL 解析拦截。
>   - **助手应用（Assistant 独立应用类型）的同等改造**——本期仅覆盖工作流画布中的「助手」节点（内部类型 `agent`）；独立助手应用无数据库配置入口，不在范围。
>   - **缓存的分布式失效通知 / 基于 binlog 的自动失效**——本期只提供 TTL + 手动刷新，不做表结构变更的自动探测。
>   - **视图（VIEW）、存储过程、函数等非表对象的选取**——表清单以普通表为主；视图是否随方言一并列出属实现兼容项，不做强制验收。

## 1. 用户故事

**故事 A（流程配置者 · 选表限定范围）**
作为 **配置工作流助手节点的人**，
我希望 **绑定数据库后能看到库里的表清单并勾选本次问答涉及的表**，
以便 **让助手只在我指定的表范围内生成 SQL，避免大库多表时选错表、猜错字段，也不必把全库结构暴露给模型**。

**故事 B（流程配置者 · schema 缓存提效）**
作为 **频繁调试和运行带数据库助手节点流程的人**，
我希望 **勾选表的 schema 结构可以缓存起来，缓存开关打开后下次运行直接用缓存**，
以便 **减少每次问答都要连库取元数据的开销和模型工具调用轮次，让 NL2SQL 响应更快、更稳定**。

**故事 C（流程配置者 · 缓存可控可刷新）**
作为 **数据库表结构会发生变更的流程维护者**，
我希望 **缓存有过期时间、并且我能手动刷新缓存**，
以便 **表结构改了以后能主动让助手拿到最新结构，而不必干等缓存过期或担心长期用错结构**。

**故事 D（运行使用者 · 行为兼容）**
作为 **实际触发工作流的终端用户**，
我希望 **升级后既有的数据库问答行为不变——未选表 / 未开缓存时与以前表现一致，选了表后回答更快更准**，
以便 **不产生「升级后原来能答的问题答不了」的回归**。

## 2. 验收标准

> AC-ID 在本特性内唯一，格式 `AC-NN`。
> 「配置者」= 编辑工作流的登录用户；「运行使用者」= 触发工作流执行的用户。

### 2.1 配置态：连通验证与表清单获取

| ID | 角色 | 操作 | 预期结果 |
|----|------|------|---------|
| AC-01 | 配置者 | 在助手节点打开数据库开关、填完类型/地址/库名/账号密码后，点击「获取表列表」 | 系统连接目标库并返回该库内的表清单供勾选；连接信息缺失或格式不合法时前端即拦截，不发请求 |
| AC-02 | 配置者 | 数据库类型选择不同引擎（MySQL/PostgreSQL/Oracle/SQLServer/DB2/GaussDB/DM8）后获取表清单 | 七种引擎均能按各自连接方式建连并返回表清单；某环境缺少对应驱动（如 SQLServer 的 ODBC Driver）时返回明确的、可理解的错误提示，而非原始堆栈 |
| AC-03 | 配置者 | 连接信息错误（地址不通 / 账号密码错 / 库不存在）时点击「获取表列表」 | 返回明确的连接失败业务错误（区分不了原因时至少提示「连接失败，请检查连接信息」），不保存半成品配置、不产生缓存 |
| AC-04 | 配置者 | 勾选若干表后保存流程，再次打开节点配置 | 已勾选的表被持久化并回显；重新「获取表列表」后，仍存在于清单中的已选表保持选中，已不存在于库中的表有明确的失效提示且不被静默当作有效表 |

- **AC-05** — THE SYSTEM SHALL 对单次返回的表清单设置合理上限；当库内表数量超过上限时，支持按表名关键字过滤后再选择（保证超大库下配置页可用）。
- **AC-06** — IF 获取表列表的请求执行超时, THEN THE SYSTEM SHALL 在限定时间内返回超时提示并允许用户重试，不得长时间挂起。

### 2.2 运行态：选表 + Schema 预取

- **AC-07** — WHERE 节点勾选了一个或多个表, THE SYSTEM SHALL 在 SQL Agent 执行问答时，将其可见/可用的表限定为被勾选的表，模型不得引用未勾选的表生成 SQL。
- **AC-08** — WHERE 节点勾选了表, THE SYSTEM SHALL 一次性向模型提供这些表的 schema 结构信息（至少含表名、列名、列类型；主键/注释等随方言能力尽力提供），使模型无需再通过「先列表、再逐表取结构」的工具调用来获得这些信息。
- **AC-09** — WHERE 节点未勾选任何表（留空）, THE SYSTEM SHALL 保持既有行为（SQL Agent 运行时自行列表、自行取 schema），与升级前完全一致。
- **AC-10** — WHEN 勾选的表在运行时已不存在于数据库（配置后被删除）, THE SYSTEM SHALL 忽略不存在的表、对仍存在的表正常提供 schema，并在运行日志中可辨识地记录「部分配置表不存在」；若勾选表全部不存在，给出明确错误而不是带着空结构静默执行。
- **AC-11** — THE SYSTEM SHALL 保证选表 + schema 预取路径下，SQL Agent 仍然只执行查询类语句（沿用既有「仅 SELECT、禁止增删改」的约束口径，不因本次改造放宽）。

### 2.3 缓存：开关、命中、TTL、刷新、降级

- **AC-12** — THE SYSTEM SHALL 提供「Schema 缓存」开关，默认关闭；关闭时行为与无缓存完全一致（每次运行实时连库取 schema）。
- **AC-13** — WHERE 缓存开关开启 AND 本次取数范围对应的缓存存在且未过期, THE SYSTEM SHALL 直接使用缓存中的 schema，不连接目标数据库取元数据。
- **AC-14** — WHERE 缓存开关开启 AND 无有效缓存, THE SYSTEM SHALL 连接目标库实时获取 schema，成功后将其写入缓存并按配置的有效期保存。
- **AC-15** — THE SYSTEM SHALL 让缓存的有效期（TTL）有默认值且可被配置者感知（可采用固定默认值或提供配置项，二选一在 design 定稿）；缓存到期后下一次运行自动回源重建。
- **AC-16** — WHEN 配置者点击「刷新缓存」, THE SYSTEM SHALL 使该节点当前连接 + 选表范围对应的旧缓存失效，并立即回源获取最新 schema 重建缓存；刷新结果（成功 / 失败）有明确反馈。
- **AC-17** — IF 缓存服务不可用（Redis 异常）AND 缓存开关开启, THEN THE SYSTEM SHALL 自动降级为实时连库获取 schema，问答主流程不中断；异常被记录为可观测日志。
- **AC-18** — WHEN 配置者修改了连接信息或勾选表范围并保存, THE SYSTEM SHALL 让下次运行按新的连接/范围计算缓存，不复用旧配置的缓存（不同连接、不同表范围的缓存互不串用）。
- **AC-19** — THE SYSTEM SHALL 保证缓存内容仅含 schema 结构信息，不含任何业务数据行；数据库密码不得出现在缓存键与缓存值中。

### 2.4 兼容、隔离与安全

- **AC-20** — THE SYSTEM SHALL 保证存量工作流（无选表字段、无缓存字段）升级后行为不变：选表视为空、缓存视为关，直接走既有路径（AC-09 / AC-12）。
- **AC-21** — THE SYSTEM SHALL 按租户隔离缓存：不同租户即使连接信息相同，也不得命中彼此的 schema 缓存。
- **AC-22** — WHEN 获取表列表或运行时取 schema, THE SYSTEM SHALL 不在应用日志中输出数据库密码、完整含密连接串。
- **AC-23** — IF 同一节点被批处理（批量运行）多次触发, THEN THE SYSTEM SHALL 保证同一缓存范围不被重复回源（同一次运行内对相同连接+表范围的 schema 获取可复用），且不出现缓存写覆盖导致的错误内容。
- **AC-24** — THE SYSTEM SHALL 在七种数据库引擎上保持「选表 / 取 schema / 缓存」行为一致；方言差异（端口、库/Schema 概念、驱动参数、DM8 的 schema 传参方式）由系统内部消化，配置者只感知「数据库类型 + 地址 + 库名 + 账号」的统一表单。

## 3. 边界情况

- **缓存与表结构漂移**：TTL 内表结构变更时，缓存是陈旧的。预期对外行为 = 在有效期内沿用缓存（配置者知情并可点「刷新缓存」立即纠正，AC-16），不做自动探测。
- **连接信息改了但缓存还在**：缓存身份必须由「连接 + 表范围」派生（不含密码明文），任一变化即 miss（AC-18）；租户维度同样进入缓存身份（AC-21）。
- **勾选的表部分失效**：部分被删/改名时取 schema 跳过失效表并记录，全部失效则报错（AC-10），避免模型拿到不完整结构却无提示。
- **SQLServer 驱动依赖**：运行环境需预装 ODBC Driver 18；环境缺失时返回可理解的错误（AC-02），不要求本期解决部署问题。
- **大表数量 / 大 schema**：表清单过多走关键字过滤（AC-05）；单表 schema 文本异常大时需有基本保护（截断/上限），具体阈值是 design 决策，但对外行为是「不因超大结构导致请求失败或上下文爆炸」。
- **缓存服务故障**：降级直连数据库、不阻断问答（AC-17）；缓存写失败属非关键路径，按「窄异常 + 日志」处理，不影响本次取数结果。
- **并发/批处理**：同一范围的并发回源允许重复取（取 schema 是只读幂等操作），但不得写出错误缓存内容（AC-23）。
- **多引擎语义差异**：Oracle/DM8 等「库 ≈ Schema/用户」的产品中，「库名称」字段实际承载的语义（service_name / schema）按各引擎连接约定解释，由 design 的方言矩阵统一；对配置者保持同一表单。
- **视图**：如某方言下列表天然包含视图，允许其一并被选；不作为强制能力承诺（范围排除项）。
